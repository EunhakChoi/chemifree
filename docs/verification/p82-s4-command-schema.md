# P82 S4: generated command schema and drift check

P82 stays `in_progress`. S4 is four PRs; this record grows with each.

## Decisions (planner, taken because the user asked to follow its recommendations)

- D1. The schema is generated by `schemars` derives on the command DTOs, behind the optional `schema` feature of `chemifree-application`. The API, CLI and providers build without it; the crate's own tests enable it through a self dev-dependency.
- D2. The schema states what serde accepts and nothing more. Semantic limits (id forms, colours, 32-bit stereo group numbers, 1 to 500 commands) stay in descriptions and are reported by the server as `invalid_command`.
- D3. One shared corpus (`crates/application/tests/data/command-schema/corpus.json`) is the truth: each case says whether serde accepts it. Rust checks it through both parse paths (`serde_json::from_str::<CommandDto>` and the operation envelope's strict parser then `from_value`). Later PRs run the same cases through a JSON Schema validator (PR2) and the web's TypeScript types (PR4); a case where the schema refuses what serde accepts is not allowed.
- D4. MCP's `commands` will use the generated schema (PR3), with a size budget and a fallback to the open schema plus a schema tool.
- D6. The checked-in schema (`commands.schema.json`) has one line per `oneOf` variant and per `$defs` entry; `CHEMIFREE_BLESS_COMMAND_SCHEMA=1` regenerates it.
- D7. The analysis and export arguments are not generated: their parameter structs read enum-like fields as `Value` on purpose, so that a wrong type is reported at `parameters.<field>`.
- D8. The web's reply guards that share payload types with commands (query atoms, bond queries, hydrogens, stereo marks, settings edits) are a later follow-up.
- D9. Doc comments become schema descriptions; internal wording was replaced (`RingDirectionDto`).

## PR1 (this PR): feature, derives, golden schema, serde corpus

- 34 derives (`CommandDto` and the 33 types it reaches). Fields read by the `nullable` deserializer (required, may be null) get `schema_with = nullable::<T>` so the schema requires the key; ring size and pattern get `{integer, enum [5, 6]}` and `{string, enum [single, kekule]}`; `add_atom.positions` gets an object schema without null, as `distinct_keys` reads a map.
- Golden schema: 96 lines, 32,077 bytes, 54 variants, 33 definitions, `additionalProperties: false` on every variant. The root is a `oneOf` without `"type": "object"`, so PR3 must wrap it for rmcp's tool schemas.
- Corpus: 75 cases (39 accept, 36 reject; 6 raw text). Six cases carry a `schema` override with a reason: JSON Schema `integer` admits `5.0` and `1.0`, and repeated keys cannot be expressed.

### Checks run

- `cargo nextest run --workspace` (as in `npm run check`): both new tests pass; `cargo clippy --workspace --all-targets` and with `--features schema`; `cargo tree -e no-dev,features` shows no `schema` feature in the normal graph.
- Mutations caught: ring enum `[5, 6, 7]` (golden); `nullable` removed from `set_bond_mark.mark` (corpus "mark missing" accepted); `serde(default)` in its place (corpus and golden); `distinct_keys` replaced (raw duplicate case accepted).

### Limits

- Schema verdicts are not machine-checked until PR2 adds the validator.
- `int64` is a format only, so serde's integer bounds are not in the schema; a stereo group number of 3000000000 passes serde and is refused by the domain.
