# Chemifree 새 세션 인계

이 문서는 완료된 작업과 다음 개발 경계를 전달한다. 인계 문서를 읽는 것만으로 다음 기능 구현을 시작하지 않으며, 새 세션에서 사용자가 요청한 범위를 따른다.

`positions`에 같은 키가 두 번 오면 본문 자체가 잘못된 것이라 다른 잘못된 본문처럼 명령 번호 없는 invalid_request이며 HTTP·CLI 모두 contract smoke로 확인), 500개 add_atom × 인스턴스 20개처럼 큰 트랜잭션은 HTTP 256 KiB 한도를 넘을 수 있어 나누거나 CLI(1 MiB)로 보내야 한다(CONTRACT.md "Edits"), `add_instance`·`move_instance`·`delete_instance`(마지막 인스턴스 삭제 거절)가 생겼다. 원자 삭제는 모든 인스턴스의 위치를 같은 변경 집합에서 지우고, 이력 항목은 그래프·인스턴스·위치 변경을 따로 기록하되 Undo/Redo는 한 번에 되돌린다. v1 응답은 기존 필드를 그대로 두고 `atoms[].position`을 첫 인스턴스 위치로 정했으며 `molecule`·`scene`을 더했다. 저장 형식은 document·draft 모두 version 2이고, version 1 파일·초안은 읽을 때 메모리에서 `s1` 하나로 옮긴다(ID·revision·제목·undo/redo 유지, 이동만 한 항목은 위치 변경만). v2는 원자 추가·삭제를 원자+위치 두 변경으로 세므로 v1 이력이 v2 한도(100 000 변경)를 넘을 수 있고, 그때는 편집과 같이 오래된 undo부터 잘라낸다(잘린 항목은 되돌릴 수 없고 원래 바이트는 첫 저장 때 migrated/에 남음, providers 테스트로 고정). 읽기는 쓰지 않으며, version 1 파일을 처음 덮어쓰는 저장은 그 바이트를 `migrated/<id>.v1.json`에 먼저 flush해 둔다. 사본은 덮어쓰지 않는다: 같은 ID로 다른 바이트의 version 1 파일이 다시 저장되면 다음 빈 이름(`<id>.v1.2.json`, `.v1.3.json`…)에 두고, 이미 같은 바이트가 남아 있으면 새로 쓰지 않는다. 다른 버전은 이유와 함께 unreadable로 거절하고 건드리지 않는다. 웹은 인스턴스마다 그림을 그리고 Duplicate placement(마지막 인스턴스를 복사해 그만큼 비켜 놓으므로 반복해도 겹치지 않음)·이동 버튼·삭제를 두며, 원자 끌기는 시작한 인스턴스에서만 옮긴다. 인스턴스가 여럿일 때 새 원자의 다른 인스턴스 위치는 결합 상대 기준이다: 기존 원자에 `bond_to`하면 그 원자가 각 인스턴스에서 옮겨진 만큼, 같은 트랜잭션의 앞선 새 원자(`$N`)에 결합하면 그 원자에 고른 위치에서 같은 간격만큼, 결합 없는 첫 원자만 클릭 지점에서 가장 가까운 원자의 차이만큼 옮긴다. 그래서 결합 길이·방향이 모든 인스턴스에서 같다(UI 정책, core 규칙 아님, web-client-check로 확인). 연산 카탈로그의 하위 연산은 명령 행과 기능 행으로 나뉘며, 기능 행은 그것을 수행하는 명령을 `commands`로 적는다(`scene_placement` → add_instance·move_instance·delete_instance; P09 당시 P10 행들은 `[]`였고 P10에서 executable(표현만)이 되어 수행 명령을 적는다; contract 1 안에서 추가된 선택 필드). 당시에는 화학 계산이 없었고 문서당 그래프는 하나였으며, 여러 그래프·그룹·페이지→인스턴스 밖의 포함 트리·다른 장면 객체·외부 참조는 후속(P11 등)이다.
- 로드맵 P10으로 원자·결합의 기록 상태를 더했다(CONTRACT.md "Documents", "Edits", "Errors", "Document file format"). 원자는 원소 또는 query 원자(`*` any, `A` any_heavy, `Q` heteroatom, `X` halogen, 서로 다른 원소 1–10개 목록과 `negated`)이고, 수소 상태(`inferred` 기본값·개수 없음, `unknown`, `specified` 0–16), 라디칼(none·singlet·doublet·triplet·unknown), attachment point(오름차순·중복 없는 1–4)를 가진다. query 원자는 전하 0·동위원소 없음이며 v1 보기의 `element`에는 기호 대신 라벨(`*`, `![N,O]` 등)이 들어가므로 `kind`를 먼저 읽는다. 결합 차수에 aromatic·dative(begin이 공여체)·query(any 또는 single/double/triple/aromatic 중복 없는 목록)·unknown을 더했다. 모두 v1 안에서 추가한 선택 필드이며 add_atom·update_atom·add_bond·update_bond가 설정하고 Undo/Redo가 전부 되돌린다. 편집·불러온 파일·이력에 같은 규칙을 적용하고, 거절되는 조합은 명령 번호와 고정 `reason` 코드(hydrogen_count_out_of_range, query_atom_charge, query_atom_isotope, query_list_invalid, bond_query_invalid, bond_query_missing, bond_query_unexpected, attachment_points_invalid, atom_kind_conflict)를 가진 invalid_command로 v1 envelope와 연산 진단 `details`에 같이 실린다(HTTP·CLI 같은 reason·메시지, contract smoke로 확인). 형식이 틀린 값은 그대로 reason 없는 invalid_request다. 저장 형식은 version 3(압축 JSON: providers 테스트가 이력 100개 항목 × 명령 500개로 원자를 가장 넓은 원소↔query 상태 사이에서 뒤집은 50 000개 변경(트랜잭션으로 도달 가능한 최대)을 써서 문서·초안 모두 약 23 MB로 읽기 한도 64 MiB 안임을 확인, 들여쓰기 JSON은 68 MB로 실패. 100 000개 변경을 그런 상태로 채운 경우는 약 46 MB로 추정할 뿐 검사하지 않음)이고 version 1·2 파일·초안은 기본 상태로 이력과 함께 옮기며, 첫 덮어쓰기 저장 전에 `migrated/<id>.v2.json`(번호 사본, 같은 바이트 중복 없음)에 원래 바이트를 남긴다. 알 수 없는 버전은 거절하고 건드리지 않는다. 연산 카탈로그의 P10 기능 행 다섯 개는 `commands`를 가진 executable(표현만)이 되었고 `chem.validate`는 not_implemented 그대로다. CLI 텍스트 출력도 상태를 보여 준다. 웹은 원자마다 라벨 배치 하나(기호·query 라벨(목록은 캔버스에서 원소 3개 뒤 "…"), 명시·미상 수소와 개수, 동위원소·전하, 위 라디칼 점, 아래 `ap1,3`)를 계산하고 그 상자 하나로 결합 자르기(상자 밖 2pt에서 멈춤, 공간이 3pt보다 작으면 가운데 3pt 획, 뒤집히거나 사라지지 않음)·보기 상자·적중 판정(원자 중심 9pt 안 또는 라벨 상자 안)을 한다. 글자는 늘이거나 줄이지 않고 원래 폭으로 그린다: 기호와 그 앞뒤 글자는 이어 그리는 텍스트 하나이고, 기호의 예약 폭이 원자 중심에 오도록 놓으며(기호는 앞뒤 글자의 예약 폭과 실제 폭 차이의 절반, 1pt 미만만큼 어긋남), 예약 폭은 번들 글꼴(Geist)과 sans-serif 대체 글꼴의 글자별 advance를 Chromium에서 잰 상한이다(다른 글꼴은 더 넓을 수 있음). 같은 상태·결합 여부·쪽의 원자는 라벨 배치 객체 하나를 공유하고, 결합 획은 배치마다 문서가 바뀔 때만 계산하며 호버·선택은 결합·라벨 층을 다시 그리지 않는다. 배치가 여럿이면 테두리와 ID가 보기 상자 안에 들고 접근성 이름에 배치(`… in s2`)가 붙는다. 결합이 오른쪽으로 기울면 명시 수소는 기호 왼쪽(`H3C`)에 둔다. 상태를 기록한 결합 탄소는 라벨을 보이고 inferred 수소는 아무것도 더하지 않는다. 결합 종류는 모양(aromatic 실선+점선(8원자 이하 고리에 든 결합은 그 결합을 지나는 가장 작은 고리의 중심 쪽(융합 결합은 어느 고리든), 그래서 결합을 그린 방향·치환기와 상관없이 고리 안쪽, 고리 밖 결합은 양 끝 원자의 다른 이웃이 더 많은 쪽; 고리 탐색은 문서마다 한 번 하고 배치들이 공유; 맨 꼭짓점에서 줄임), dative 끝 쪽 화살표, query 점선, unknown 지그재그)과 접근성 이름으로 구별한다. 결합 도구는 언제나 끌기 시작점에서 결합을 시작하므로 dative의 공여체는 시작한 원자·점이다(빈 곳에서 원자로 끌면 원자를 추가한 뒤 그 원자에서 결합, 반대 방향의 기존 결합 위로 그리면 같은 트랜잭션에서 지우고 다시 추가해 결합 ID가 바뀜). 인스펙터 편집은 요청이 실행될 때의 최신 문서로 만들어(query 설정 시 전하·동위원소를 함께 지움, query 원자에는 전하·동위원소를 보내지 않음, 입력한 query 목록과 not은 서로의 최신 값을 유지) 빠른 연속 입력이 거절되지 않는다. 웹 클라이언트는 상태가 있는 응답과 이전 응답을 모두 받고(이전 응답은 기본값으로 채움) 일부만 있거나 섞인 응답은 거절한다. 당시에는 표현만 했으며 계산은 후속 단계로 남았다(MODEL-02.rest, P16 등).

CONTRACT.md의 Documents·MOL·SMILES·Graph identity·Substructure 절을 따른다). version 4의 장면·참조·선택·이력은 보존하고 이전 문서 덮어쓰기 및 이전 초안 복구 전 원본 바이트를 보관한다. 결합 획과 라벨이 겹칠 공간도 없는 경우 획은 생략하지만 결합은 선택할 수 있다.

NMR 데이터에서는 feature schema의 파일 해시와 항목·선언된 출처 범위를 검증하고 큰 정수와 정수인 소수·지수 표기를 정확히 보존한다. 출처 원본 파일 자체를 열거나 검증하지 않는다. 질량 입력은 원문 십진수와 binary64 참고 비트, 원소·동위원소·선택·별칭 및 정확한 큰 비영 출처 범위를 검증한다. 제공된 원문은 실제 바이트와 줄 해시도 검사한다. P14 당시 NMR·질량 계산과 feature-schema 모델 바인딩은 미구현이었다. 현재 P19가 검증된 질량 입력을 소비하며 NMR과 feature-schema 모델 바인딩은 미구현이다. 질량의 #41·#42는 리뷰 3회 한도에 따라 미병합 종료했고 이번 구현은 최신 main에서 독립적으로 다시 작성했다. 회차별 근거는 `docs/verification/review-history-batch2.md`에 있다. 명명 query·retained 패턴의 별도 predicate 선언과 XLogP 100행의 큰 family 인덱스·binary64 비트·원시 수치를 보존하지만 매칭·예측 바인딩은 미구현이다. 명명 lexicon과 두 치환 표의 바이트·순서·그래프 참조를 보존하지만 명명 문법과 모델 바인딩은 미구현이다. nickname XML의 ID·원자/결합 참조와 alphabet 후보를 보존하지만 전체 CDXML 참조 검증이나 생체고분자 확장은 미구현이다. 원문 XML의 사용자 정의 엔터티 선언은 미지원으로 거절한다. prediction 11개 파일은 유한 비트·회귀 순서·feature 해시와 출처 범위를 검사하되 전체 메타데이터의 테이블 대응 및 예측 엔진은 미구현이다. phase 4 NMR carrier의 19개 정규화 스트림과 선택적 원문을 검증하고 선언된 큰 줄 번호를 보존하지만 NMR 엔진은 미구현이다. 독립 AqSolDB CSV의 9,982행과 추가 열을 보존하고 추가 열 개수만 보고한다. 독립 NIST snapshot의 부호 있는 큰 출처·동위원소 필드와 중복 키가 없는 불투명 합계를 보존하며 현재 P19는 선택된 snapshot에 한정된 계산 정책을 적용한다. CLogP carrier의 11,987행과 원시 비트·텍스트를 보존하지만 fragment 매칭과 예측은 미구현이다. 경험 입력의 44,202행과 F32 원시 비트·십진 표기를 보존하지만 단위·그래프 매칭과 예측은 미구현이다. HELM·템플릿·명명·CMR reader는 정수인 소수·지수 입력도 정확히 읽으며, HELM ID와 템플릿·명명의 큰 생산자 숫자 및 CMR 원문 숫자를 보존한다. 독립 HELM 레코드 705개의 null·선택 필드와 철자를 보존하지만 attachment·입체·결합 규칙은 미검증이다. phase 4 템플릿 프레이밍의 20,467행을 읽지만 활성 템플릿 연결이나 생체고분자 확장은 미구현이다. phase 4 명명 자료의 텍스트·순번·생산자 파싱 보고를 보존하지만 행 사이 대응과 독립 화학 파싱은 검증하지 않는다. CMR 배열은 원시 바이트·0 기반 위치와 정확한 JSON 숫자 표기를 보존하며 미확정 수치 비트 형식이나 CMR 엔진을 추론하지 않는다. phase 4 메타데이터·binary64 literal·Real48 표를 타입으로 보존하지만 Real48 원문과 유리수의 상호 검증이나 수치 연산은 미구현이다. 윤곽 두 역할은 별도 호스트 선택과 공개 metadata 해시를 확인하고 binary64 원시 비트를 보존한다. 공개 registry 해시만으로 manifest 소속을 증명하지 않는다. HTTP·CLI·웹은 데이터 상태를 표시하고 데이터가 없어도 편집할 수 있다. 신뢰된 host가 개별 등록을 선택하며, 집계 registry 해시만으로 특정 manifest의 소속을 증명하지 않는다. 실제 개인 DATA와 의존 모델은 검증하지 않았으며 데이터 로딩은 화학 엔진이 아니다. 정확한 선택 방법과 한계는 [DATA.ko.md](DATA.ko.md)에 있다.
- P14의 manifest에 선택 원문 파일이 포함돼 있어도 그 파일이 없으면 정규화 자료를 읽을 수 있다. 필수 파일의 누락과 존재하는 선택 파일의 손상·접근 오류는 계속 거절한다.
- P14의 공통 U64와 phase 6 원소 기호·타입 원소·명명 순위 reader는 정수값인 소수·지수 표기를 원문에서 정확히 읽는다. 명명 label·query·retained pattern·lexicon과 nickname의 출처 인덱스도 최대 4096자리까지 정확히 보존한다. 선택 원본과 범위의 대응이 공개 계약에 명시되고 원본이 제공된 경우에만 실제 범위를 대조한다. 예측·질량과 phase 4 CLogP·경험 자료도 불활성 출처 정수를 최대 4096자리까지 정확히 보존하며, 실제 배열 참조와 명시된 정수 폭은 별도로 제한한다. phase 7 명명 reader에는 명세의 별도 정수 토큰 규칙을 유지한다.
- P15의 수치 기반 범위는 완료됐다. `chemifree-numerics`는 부호 있는 정확한 유리수와 Real48·binary32·binary64·80비트 확장 형식의 원시 저장 비트 사이를 명시된 반올림으로 변환한다. 유한 사칙연산의 중간 저장은 호출자가 형식을 선택하고, 비유한 값·지원하지 않는 부호화·0 제수·오버플로는 오류로 다룬다. 선택된 각도 계산은 확장 중간 연산의 순서와 binary64 저장을 지키며 불규칙도는 반쪽을 위로 반올림한다. 컴퓨터 point 등 길이 단위와 명시적 양수 몰질량을 쓰는 Real48 mol/L–g/L 변환은 독립 물리 정책으로 제공한다. 6자리 기본·0–8자리 고정 문자열과 정확한 유리수의 3자리 반올림 후 F32 저장은 서로 다른 정책이다. 다른 화학 단위·레거시 상수와 화학 결과 UI는 아직 미구현이다. 일반 계산 정밀도는 계속 `not_implemented`이고 P19는 질량 표시 자릿수만 별도로 저장해 새 결과에 적용한다. 경계와 독립 기준은 [NUMERICS.ko.md](NUMERICS.ko.md)에 있다.
- 이후 문서나 코드가 변경될 수 있으므로 작업 시작 시 git status, git log와 현재 CI를 다시 확인한다. 기존 사용자 변경은 보존한다.

- 임시 stdin probe에서 no-raw-colors와 no-restyle 탐지를 확인했다. 그 probe가 기본 설정을 변경하지는 않았다.
- Base UI의 내비게이션은 일반 anchor + buttonVariants를 사용한다. Button render anchor 패턴은 링크를 button 역할로 바꾸므로 재도입하지 않는다.

## 알려진 한계

보장과 한계의 기준 목록은 CONTRACT.md의 "Guarantees and known limits"다. 리뷰와 변경은 그 목록에 맞춰 판단한다. 아래는 구현 관점의 보충이다.

- 작업 사본은 API 프로세스 메모리에 있다. 프로세스가 끝나면 마지막 커밋과 마지막 복구 초안이 남는다. 마지막 초안 이후의 편집(웹이 열려 있으면 보통 1–5초, 다른 클라이언트만 있으면 2–10초, 초안 쓰기가 실패·차단 중이면 더 길다)은 비정상 종료 시 사라진다.
- API 프로세스가 클라이언트 없이도 초안을 쓴다(DraftWriter, 250ms마다 확인). 마지막 변경 2초 뒤, 초안에 없는 첫 변경 10초 이내(연속 편집으로 미루지 못함). 실패하면 2·5·15초 뒤, 이후 30초마다 재시도하고 편집이 재시도를 미루지 않으며 session.draft_failure로 알린다. 정상 종료(SIGTERM·Ctrl+C) 때는 마지막 요청 응답 뒤 모든 세션을 즉시 초안으로 쓰고, 못 쓴 문서는 로그에 남긴다. 웹 자동 저장과 같은 문서 차례(최대 3초 대기 후 busy, 실패로 기록해 재시도)를 지키므로 한 리비전을 두 번 쓰지 않는다. 주기적 초안 쓰기는 차례가 잡힌 문서(저장 중 등)를 기다리지 않고 다음 확인(250ms 뒤)에 다시 시도하므로, 바쁜 문서가 다른 문서의 초안을 늦추지 않는다(실패로 세지 않음). 초안 쓰기(웹 자동 저장·서버 주기 쓰기·종료 전 쓰기)는 세션 표에서 그 순간의 사본만 떠 두고 표를 놓은 채 디스크에 쓴다. 디스크가 멈춰도 다른 문서의 요청과 같은 문서의 편집·읽기는 진행되며, 같은 문서의 차례를 기다리는 저장·닫기 등만 기다린다(최대 3초 후 busy). 쓰는 동안 들어온 편집은 초안에 들어갔다고 표시하지 않고(draft_revision은 쓴 리비전) 그 첫 편집부터 다시 일정을 센다. 쓰는 중인 깨끗한 세션은 자리 확보를 위해 닫지 않는다. 서버의 주기적 초안 쓰기와 종료 전 쓰기는 문서마다 별도 스레드에서 실행하므로 한 문서의 쓰기가 멈춰도 다른 문서의 초안은 계속 쓰이고, 쓰는 중인 문서는 다음 확인에서 다시 시작하지 않는다(종료는 멈춘 쓰기가 끝날 때까지 기다린다). 쓰는 동안 그 문서의 응답은 쓰기를 시작할 때 확인한 복구 상태를 보여 주고 저장소를 다시 확인하지 않으며, 파일 저장소의 초안 소유권 확인 잠금은 문서별이라 다른 문서의 초안 상태 확인을 막지 않는다. 정상 종료 때는 실행 중인 요청이 없고, 진행 중인 서버 초안 쓰기가 끝나기를 기다린 뒤 문서마다 차례를 최대 3초 기다린다. 웹은 session.draft_failure(누가·언제 재시도하는지, 시도 횟수, code·reason과 사용자 조치)를 그대로 표시하고, 기록하는 서비스에서는 직접 다시 초안을 쓰지 않고 서비스 재시도 시각 1초 뒤 문서를 다시 읽는다(읽기가 실패하면 2·5·15·30초 backoff로 다시 읽음). 문서를 읽을 때 세션 토큰을 먼저 확인해 화면의 view를 그 프로세스에 묶고, 이 읽기는 토큰이 같은 프로세스인지 확인하므로, 실패 중 API가 재시작되면 새 프로세스의 저장본을 받아들이지 않고 '중지'로 바꾼 뒤 그림을 화면에 둔 채 Reload를 요구한다. 필드가 없는 이전 v1 서비스에서는 페이지가 직접 재시도한다(필드·code·reason은 v1 안에서 추가되어 선택 사항). 버려진 초안이나 다른 프로세스 소유 초안은 덮어쓰지 않고(recovery_pending·draft_in_use로 실패·재시도) 초안은 만료되거나 자동 정리되지 않는다(복구·사본 복구·discard-draft로만 제거). CLI는 편집마다 커밋하므로 초안을 쓰지 않는다.
- 저장은 문서의 차례만 잡고 저장소(다른 프로세스의 저장 잠금 대기 포함)를 기다린다. 그동안 다른 문서 요청과 같은 문서의 편집은 진행되고, 저장은 요청한 리비전을 커밋한다. 커밋·초안을 다루는 작업(저장·자동 저장·닫기·복구·초안 버리기·사본)은 문서별 차례로 직렬화되며, 차례는 최대 3초, 다른 프로세스의 저장 잠금은 최대 5초 기다린 뒤 busy로 거절한다(아무것도 바꾸지 않음).
- 대기는 상한이 있지만 저장소 I/O 자체는 그렇지 않다. 생성·닫기·복구·초안 버리기·사본은 세션 표를 잡은 채 I/O를 하므로(초안 쓰기는 예외, 위 항목) 디스크가 멈추면 같은 프로세스의 다른 요청도 그만큼 기다린다. 실행 중인 request_id에 대한 request_in_progress 응답만은 이를 기다리지 않는다(별도의 작은 표로 확인).
- 저장 잠금과 초안 소유 잠금은 OS advisory lock(std File::lock, Unix flock)이다. Chemifree 프로세스끼리만 지켜지며 일부 네트워크 파일 시스템에서는 보장되지 않는다. locks/와 drafts/*.owner 파일은 의도적으로 지우지 않는다.
- 한 프로세스 안의 요청들은 초안 소유 잠금을 한 번에 하나씩 잡는다. OS 파일 잠금은 같은 프로세스의 다른 핸들도 거절하므로, 그러지 않으면 동시에 들어온 요청이 다른 요청의 잠깐 확인을 다른 프로세스의 소유로 오인해 버려진 초안을 Draft in use로 보였다(#8 조사 중 발견).
- 같은 데이터 디렉터리에 API 프로세스가 둘이면 같은 문서의 초안은 한쪽만 소유한다. 다른 쪽 autosave는 draft_in_use로 거절된다. 실시간 병합은 없다.
- 문서당 초안은 하나다. 버려지지 않은 초안이 있으면 새 작업의 자동 저장은 멈추고(화면에 '일시정지'로 표시) 사용자가 복구·버리기를 정해야 한다. 초안은 만료되지 않는다.
- 웹의 초안 상태는 서버 응답(session.draft_revision, recovery)만으로 판단한다. 페이지가 따로 기억하는 것은 대기 시간과 재시도 일정뿐이고, 문서가 바뀌면 처음부터 다시 센다. 문서를 떠나기 전에는 대기 중인 작업의 초안을 먼저 쓴다.
- request_id 재전송 기억은 프로세스 메모리(문서당 최근 64개, 생성·닫기는 프로세스 단위)에만 있다. 응답을 잃은 요청을 다시 물으면 이 재생 창 안에서만 원래 응답을 돌려주고, 그 밖이면 다시 실행된다. 웹은 응답을 받지 못한 저장을 같은 ID로 즉시 한 번, 진행 중이면 1초마다 최대 12번 더 묻고, 그래도 답이 없으면 실패가 아니라 'Save not confirmed'로 표시한다. 생성·사본 요청의 ID도 진행 중인 동안과 응답이 없을 때 유지한다. 그 사이 API가 재시작되면 재전송하지 않고(중복 생성 방지) 문서가 이미 생겼을 수 있다고 안내하며 목록을 새로 고친다. 확인은 사용자 몫이다.
- revision은 2^53 − 1까지다. 편집은 2^53 − 2에서 멈추고 마지막 번호는 버린 뒤 다시 여는 사본용으로 남긴다. 그 뒤 다른 저장을 따라갈 번호가 없으면 그 프로세스에서는 resource_limit으로 거절한다.
- 사본은 내용·ID 카운터만 가져가고 Undo 이력은 비운 채 revision 0에서 시작한다. 사본으로 저장하면 원본 세션은 닫히고(미저장 변경은 사본에만 남음) 원본은 마지막 저장본으로 다시 열린다. 원본 초안을 지울 수 없으면 원본 세션은 미저장 변경·초안과 함께 남고(closed: false), 웹은 사본 안내에서 그 사실과 원본 열기를 보여 준다(#7). 안내는 사본을 만든 순간의 사실이라 다른 문서로 넘어가거나 서비스 재시작을 알게 되면 지운다. 재시작은 쓰기 요청의 세션 토큰이 거절될 때 알게 되므로, 쓰기가 없으면 그때까지는 안내가 남는다.
- 세션 64개가 모두 열린 상태에서 사본이 들어갈 자리가 필요하면 미저장 변경이 없는 세션 중 ID가 가장 작은 것을 닫는다. 초안을 사본으로 복구할 때 사본 생성 자체는 다른 clean 세션이 없을 때만 원본을 퇴거한다. 초안 제거 중 다른 요청이 원본을 퇴거할 수도 있으며, source.closed는 응답을 기록할 때 원본 세션이 닫혔는지를 알린다(#6).
- 읽기 전용 저장소는 reason read_only로 알리지만, 읽기 전용으로 열기나 다른 위치에 저장하기는 없다. Chemifree 외 프로그램에 대한 파일 잠금은 없다.
- 삭제는 휴지통(trash/)으로 옮기는 것이다. 열린 사본에 미저장 변경이 있거나 복구 초안(버려진 것이든 다른 프로세스 소유든)이 있으면 거절하고, 저장 잠금과 초안 소유 잠금 아래에서 rename 한 번으로 옮긴다. 영구 삭제와 휴지통 비우기는 아직 없다. 다른 프로세스의 깨끗한 사본은 다음 접근에서 닫히고, 미저장 사본은 저장·초안으로 문서를 되살리지 못한다(save_conflict, document_not_found). 초안이 아직 없는 다른 프로세스의 미저장 작업은 CLI가 볼 수 없으므로, 그 작업은 사본 저장으로만 지킬 수 있다.
- 목록 검색·정렬은 Application이 한다(웹·CLI는 질의만 전달). 정렬 recent는 저장 파일의 수정 시각(벽시계) 기준이라, 시계 조정(시간 동기화로 시계가 뒤로 가는 경우 등) 사이에 저장된 문서는 순서가 바뀔 수 있다(WSL2에서 실제로 관찰). 이름 변경은 미저장 변경이 없는 문서에서만 즉시 커밋된다.
- 이름 변경·삭제·복원도 저장과 같은 문서 차례(최대 3초 후 busy)를 따르고, 실행 중인 같은 request_id는 즉시 request_in_progress를 받는다. 재전송 기록은 이름 변경이 문서별(세션), 삭제·복원이 프로세스별이다. 웹은 응답을 못 받으면 같은 request_id로 한 번 다시 묻고 진행 중이면 1초마다 묻는다. 그 뒤의 재시도는 새 요청이며, 첫 시도가 이미 반영됐다면 전제 조건(revision, 휴지통 여부)이 거절한다(revision_conflict, document_not_found).
- revision·ID 재사용 방지 기억은 프로세스 메모리에 있다. API가 재시작되면 웹은 문서를 다시 읽어 화면과 같은 내용일 때만 편집을 재전송하고(Undo/Redo 제외), 다르면 Reload를 요구한다. CLI는 매번 저장본에서 시작한다.
- request_id 재전송 기록은 원래 응답 전체를 보관한다(세션당 64개). 큰 문서를 많이 열면 메모리 사용이 커질 수 있다.
- 문서 목록은 저장된 각 문서를 전부 복원·검증한다. 문서가 많고 크면 목록 조회가 느릴 수 있다(잠금 밖에서 수행).
- 화면에서 만든 편집이 앞선 요청에 밀려 낡으면 revision_conflict로 거절되고 Reload를 안내한다(전하 ± 같은 상대 편집은 최신 상태 기준으로 계산).
- 문서당 화학 그래프·페이지는 하나다. 장면 인스턴스는 최대 20개이며 그룹과 단순 선·사각형·화살표 및 명시적 참조를 기록한다. 여러 그래프·페이지, 텍스트 등 고급 장면 객체, 반응 의미, 화면 확대·이동은 아직 없다.
- version 1 초안은 복구해도 그 세션의 다음 초안 쓰기나 저장 전까지 디스크에 version 1로 남는다(읽을 때마다 다시 옮김). migrated/의 보관본은 Chemifree가 지우거나 목록에 보이지 않으며, 정리는 사용자 몫이다.
- 캔버스는 포인터 중심이다. 키보드만으로 원자를 배치하는 접근 경로는 없다(인스펙터 편집과 단축키는 있음).
- CI의 browser job은 Ubuntu 24.04에서 잠근 playwright-core가 가리키는 Chromium을 시스템 라이브러리와 함께 설치하고, test:browser:routes와 test:browser를 재시도 없이 한 번씩 실행한다. route 검사가 실패해도 smoke는 실행한다. CHEMIFREE_SMOKE_NO_SKIPS=1이라 root 실행 등으로 건너뛴 단계가 있으면 실패한다. 통과·실패와 관계없이(빌드 실패 포함) results.json, build.log, environment.json, requests.log, api.log, web.log, 스크린샷(실패 시 failure.png)을 artifact로 14일 보관한다. 일부러 깨뜨린 빌드로 이 job이 실패하는지 확인한 기록은 verification/browser-ci.json에 있다. 포트 3001·5173을 쓰므로 한 러너에서 동시에 두 번 실행할 수 없다.
- 브라우저 smoke에서 초안 버리기·사본 저장 직후 API를 죽이는 단계는 그 작업이 뒤따라 보내는 목록 읽기 응답을 기다린 뒤 죽인다. CI(run 40652695710)에서 강제 종료가 이 읽기를 끊어 Vite 프록시가 502로 답해 한 번 실패했다. 제품 결함이 아니라 테스트 동기화 문제이며 같은 순서가 main에도 있었다.
- 브라우저 smoke의 '재시작 모의' 단계가 가끔 실패하던 문제(#8)는 제품 결함이 아니라 테스트 동기화 문제였다. Playwright 1.56.1은 마지막 page route가 사라지면(times: 1 route 소진, unroute) 요청 가로채기를 끈다. 그 순간 시작된 요청은 브라우저에 멈춘 채 서버에 닿지 않고 10초 뒤 클라이언트가 중단한다. smoke는 컨텍스트 전체에 통과용 route를 두어 가로채기를 끄지 않는다(scripts/lib/request-interception.mjs). npm run test:browser:routes가 Chemifree 코드 없이 이 경쟁을 재현한다. 재전송 편집 확인은 스피너 상태에만 기대지 않고 실제 200 응답을 기다린다. 실패하면 failure.png, requests.log, api.log(--log-requests), web.log를 남기고 임시 디렉터리를 지우지 않는다. 기록은 verification/browser-route-race.json.

## 다음 구현 단위 제안

사용자 요청이 범위를 정한다. P11은 #34와 이전 초안 보관을 다룬 #35로, P12는 #36으로 병합됐다. P14의 마지막 구현은 #69로, P15의 수치 기반 구현은 #75로 병합됐고 각각 병합 후 main CI도 통과했다. PR·리뷰·병합 상태는 GitHub와 `docs/verification/review-history-batch2.md`에서 확인한다. 그 밖의 후보:

1. 저장·복구 후속(필요 시): 휴지통 영구 삭제·비우기, 초안 만료 정책(현재는 만료 없음), 읽기 전용 모드.
2. 형식 입출력: 구현된 MOL/SDF V2000, CDXML, CDX와 SMILES 부분을 유지하고 SMILES 입체·InChI 및 고급 필드는 별도 작업으로 진행한다. 외부 형식의 거절·수정·손실을 항목별로 정하고 보고한다. 조용한 수정은 하지 않는다.
3. 화학 그래프 진단: 제한된 원자가·물성·방향족·그래프 동등성 검사와 부분구조 검색을 유지하고 더 넓은 모델을 검증한다. 고리·차수·수소 개수 같은 질의 조건은 먼저 기록 상태가 필요하다.
4. 편집기 확장: 고리 템플릿, 확대·화면 이동과 추가 장면 객체.
5. 사용자 인증·원격 배포는 별도 접근 제어 설계 후 진행.

명명·NMR·물성·고급 형식·Windows bridge·팀 서비스를 한꺼번에 넣지 않는다. 기능을 실제로 연결하고 검증한 뒤 capability 상태를 변경한다.

## 독립 구현 경계

제품 코드는 새 컨텍스트에서 공개 기능 명세와 독립적인 자료만으로 작성한다. 원본 바이너리·원본 코드/디컴파일·조사 evidence·private vendor payload를 열지 않는다. GitHub 저장소의 현재 독립 소스와 검증·설계 문서는 구현 입력으로 사용할 수 있다.

기존 분석 인계와 원시 데이터가 공개 저장소에 포함되어 있다고 가정하지 않는다. 필요한 명세는 승인된 공개 인계에서 기능별로 읽고, 원본 분석을 다시 시작하거나 전체 자료를 공개 저장소에 복사하지 않는다.

기존 개인용 모델 데이터와 서비스용 데이터셋은 별도 범위다. 사용자 결정은 로컬 보조 인계와 실제 요청을 따른다. 원본 실행 엔진이나 가짜 수치로 미구현 기능을 대체하지 않는다.
